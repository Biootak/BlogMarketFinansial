# JWT Compatibility Tests

## Overview

This test suite verifies that JWT tokens generated by the Go backend are fully compatible with the Next.js frontend (using NextAuth v5), and vice versa. This is critical for the gradual migration strategy where both systems need to accept tokens from each other.

## Property Being Tested

**Property 38: JWT Token Cross-Compatibility**
> For any JWT token generated by the Go backend, it should be valid for authentication in the Next.js frontend, and vice versa.
> 
> **Validates: Requirements 11.2**

## Test Categories

### 1. Token Structure Compatibility Tests

These tests verify that Go-generated tokens have the exact structure expected by NextAuth:

#### Test: Go-generated token has NextAuth-compatible structure
- **Purpose**: Verify token claims match NextAuth expectations
- **Validates**:
  - Uses `sub` field for user ID (NextAuth convention)
  - Contains `email`, `name`, `role` fields
  - Contains `emailVerified` field (nullable)
  - Has standard JWT claims: `exp`, `iat`, `nbf`

#### Test: Token expiration matches NextAuth (3 days)
- **Purpose**: Verify session duration matches NextAuth configuration
- **Validates**:
  - Token expires in exactly 3 days (259200 seconds)
  - Matches NextAuth `session.maxAge` setting

#### Test: Token uses HS256 algorithm (same as NextAuth)
- **Purpose**: Verify signing algorithm compatibility
- **Validates**:
  - Uses HS256 (HMAC with SHA-256)
  - Same algorithm as NextAuth default

#### Test: Token with nil emailVerified is compatible
- **Purpose**: Verify nullable fields work correctly
- **Validates**:
  - Tokens can be created with null `emailVerified`
  - Compatible with unverified users in NextAuth

### 2. Claims Round-Trip Tests

These tests verify that user information survives encoding and decoding:

#### Test: All user information survives round trip
- **Purpose**: Verify no data loss in token generation/validation cycle
- **Validates**:
  - UserID, Email, Name, Role are preserved exactly
  - EmailVerified timestamp is preserved
  - All fields can be extracted correctly

#### Test: Token can be refreshed maintaining user data
- **Purpose**: Verify refresh token functionality
- **Validates**:
  - Refreshed token contains same user data
  - Refreshed token has new expiration time
  - Refreshed token is different from original

### 3. Secret Compatibility Tests

These tests verify that the same secret produces compatible tokens:

#### Test: Same secret produces verifiable tokens
- **Purpose**: Verify tokens work with shared secret
- **Validates**:
  - Go and Next.js can use same `AUTH_SECRET`
  - Tokens signed with shared secret are valid

#### Test: Different secret fails validation
- **Purpose**: Verify security of token validation
- **Validates**:
  - Tokens signed with different secrets are rejected
  - Prevents token forgery

### 4. Integration Tests (Requires Both Servers)

These tests require both Go backend (port 8080) and Next.js frontend (port 3000) to be running:

#### Test: Go-generated token with Next.js
- **Purpose**: End-to-end test of Go → Next.js compatibility
- **Setup**: 
  1. Register user via Go API
  2. Get JWT token from Go
  3. Use token to authenticate with Next.js API
- **Validates**: Next.js accepts Go-generated tokens

#### Test: Next.js-generated token with Go
- **Purpose**: End-to-end test of Next.js → Go compatibility
- **Setup**:
  1. Register user via Next.js API
  2. Get JWT token from Next.js
  3. Use token to authenticate with Go API
- **Validates**: Go accepts Next.js-generated tokens

#### Test: JWT refresh token compatibility
- **Purpose**: Verify refresh tokens work across both systems
- **Setup**:
  1. Generate token via Go
  2. Refresh token via Go
  3. Verify new token works with both Go and Next.js
- **Validates**: Refreshed tokens are cross-compatible

## Running the Tests

### Unit Tests (No servers required)
```bash
# Run all unit-level compatibility tests
go test -v ./tests/integration/jwt_compatibility_test.go -short

# Run specific test
go test -v ./tests/integration/jwt_compatibility_test.go -run TestJWTTokenStructureCompatibility
```

### Integration Tests (Requires both servers)
```bash
# Start Next.js server (terminal 1)
npm run dev

# Start Go server (terminal 2)
go run cmd/server/main.go

# Run integration tests (terminal 3)
go test -v ./tests/integration/jwt_compatibility_test.go
```

## Configuration Requirements

Both Go and Next.js must use the same `AUTH_SECRET` environment variable:

```env
# .env (Go)
AUTH_SECRET=your-secret-key-minimum-32-characters

# .env.local (Next.js)
AUTH_SECRET=your-secret-key-minimum-32-characters
```

## NextAuth Configuration Reference

The Go JWT implementation is designed to match this NextAuth configuration:

```typescript
// src/auth.ts
export const { handlers, auth, signIn, signOut } = NextAuth({
  session: {
    strategy: 'jwt',
    maxAge: 3 * 24 * 60 * 60, // 3 days
    updateAge: 24 * 60 * 60,  // 24 hours
  },
  callbacks: {
    async jwt({ token, user }) {
      if (user) {
        token.role = user.role || 'USER';
        token.id = user.id;
        token.emailVerified = user.emailVerified;
        token.email = user.email;
        token.name = user.name;
      }
      return token;
    },
    // ...
  },
  // ...
});
```

## Token Structure

### Go-Generated Token Claims
```json
{
  "sub": "user-id",              // User ID (NextAuth uses "sub")
  "email": "user@example.com",
  "name": "User Name",
  "role": "USER",                // USER, AUTHOR, ADMIN, SUPER_ADMIN
  "emailVerified": 1234567890,   // Unix timestamp (nullable)
  "exp": 1234567890,             // Expiration (3 days from now)
  "iat": 1234567890,             // Issued at
  "nbf": 1234567890              // Not before
}
```

### NextAuth Token Claims
```json
{
  "sub": "user-id",              // User ID
  "email": "user@example.com",
  "name": "User Name",
  "role": "USER",
  "emailVerified": "2024-12-06T10:30:00.000Z", // ISO string or null
  "exp": 1234567890,
  "iat": 1234567890
}
```

## Compatibility Guarantees

✅ **Algorithm**: Both use HS256 (HMAC with SHA-256)
✅ **Secret**: Both use `AUTH_SECRET` environment variable
✅ **Expiration**: Both use 3-day session duration
✅ **Claims**: Both include `sub`, `email`, `name`, `role`, `emailVerified`
✅ **Validation**: Both validate signature, expiration, and claims

## Migration Strategy

During gradual migration:

1. **Phase 1**: Both systems generate their own tokens
   - Go validates Go tokens
   - Next.js validates Next.js tokens

2. **Phase 2**: Cross-validation enabled
   - Go validates both Go and Next.js tokens
   - Next.js validates both Next.js and Go tokens

3. **Phase 3**: Go becomes primary
   - All new tokens generated by Go
   - Next.js only validates (doesn't generate)

4. **Phase 4**: Complete migration
   - Only Go generates and validates tokens
   - Next.js API routes removed

## Troubleshooting

### Token validation fails
- **Check**: Both systems use same `AUTH_SECRET`
- **Check**: Token hasn't expired (3 days)
- **Check**: Token format is correct (Bearer token)

### Claims mismatch
- **Check**: Field names match (`sub` vs `id`)
- **Check**: Data types match (timestamp vs ISO string)
- **Check**: Nullable fields handled correctly

### Integration tests fail
- **Check**: Both servers are running
- **Check**: Ports are correct (8080 for Go, 3000 for Next.js)
- **Check**: Database is accessible to both systems
