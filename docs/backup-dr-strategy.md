# استراتژی بکاپ و Disaster Recovery — راهکار واقعی شرکت‌های بزرگ

> سؤال: شرکت‌های بزرگ چطور کاری می‌کنند که دیتاشان «هیچ‌وقت» پاک نشود؟
> جواب کوتاه: **هیچ‌کس به یک فروشنده یا یک کپی اعتماد نمی‌کند.** اصل
> «تک‌نقطهٔ شکست ممنوع» است — دیتا باید همیشه در چند نسخه، چند مکان و چند
> فناوری مستقل باشد و بازیابی آن هر از گاهی **تست** شود.

نسخهٔ «غیرقابل‌تغییر» یعنی بکاپی که حتی با دسترسی admin هم قابل حذف نیست
تا مدت مشخص (Object Lock / WORM در S3، یا tape آفلاین). این همان چیزی است که
بزرگ‌ها را در برابر باج‌افزار و خطای انسانی نجات می‌دهد — نه فقط «بکاپ داشتن».

## ۲) RPO و RTO — قراردادهای خودت را مشخص کن

- **RPO (Recovery Point Objective):** چقدر دیتا می‌توانی از دست بدهی؟ مثلاً
  «حداکثر ۲۴ ساعت» یعنی بکاپ روزانه کافی است.
- **RTO (Recovery Time Objective):** چقدر طول می‌کشد سایت برگردد؟ مثلاً «کمتر
  از ۲ ساعت» یعنی IaC + بکاپ آماده که با چند دستور deploy شود.

شرکت‌های بزرگ برای دیتابیس‌های حیاتی RPO را با **PITR** (Point-in-Time
Recovery) به چند دقیقه می‌رسانند: بکاپ کامل + replay پیوستهٔ WAL. معادل ساده
برای این پروژه: بکاپ روزانهٔ `pg_dump` + اگر واقعاً حیاتی شد، `pg_basebackup`
هر چند ساعت + آرشیو WAL (`archive_mode=on`) روی S3.

## ۳) چه چیزی باید بکاپ شود (و چه چیزی نه)

| چیز | چرا |
|-----|-----|
| کد (این ریپو) | در git — همیشه قابل بازسازی است |
| زیرساخت (OpenTofu) | در git — با `tofu apply` دوباره ساخته می‌شود |
| **دیتابیس** | **تنها چیز غیرقابل‌بازسازی** — پست‌ها، کاربران، نرخ‌ها، تنظیمات |
| فایل‌های آپلود (public/uploads) | اگر روی دیسک اپمرال باشند با هر deploy می‌پرند |
| secretها (`.env`) | در git **نرو**؛ در یک vault/بکاپ جدا نگه دار |

بزرگ‌ها دیتا را از کد جدا می‌کنند: کد را می‌توان از git بازسازی کرد، ولی
دیتا فقط از بکاپ — پس تمام تمرکز بکاپ روی دیتاست.

## ۴) چرا «بکاپ داخل همان پلتفرم» کافی نیست

اگر بکاپ در Object Storage همان فروشنده (گوزونگا) باشد، با **حذف اکانت** همه‌چیز
با هم می‌پرد — بیلینگ پالیسی گوزونگا (بخش ۶) و پرایوسی پالیسی (بخش ۵.۲) هیچ
دورهٔ نگهداری بعد از termination تضمین نمی‌کنند. به همین دلیل نسخهٔ دوم باید
**خارج از پلتفرم** باشد: یک S3 دیگر، یک سرور دیگر، یا حتی دانلود ماهانه روی
دیسک خودت. این دقیقاً همان «۱ نسخهٔ خارج از محل» در قانون 3-2-1 است.

## ۵) لایه‌های دفاعی که این ریپو پیاده می‌کند

1. **بکاپ JSON اپ** (`/api/cron/backup` → `lib/backup.ts`) هر شب — بازیابی سریع
   محتوای سایت، آینه‌شده در `S3_BACKUP_BUCKET`.
2. **بکاپ واقعی Postgres** (`scripts/backup-db.mjs`) هر شب ۰۳:۳۰ — `pg_dump -Fc`
   + آپلود به دو مقصد S3 (داخل پلتفرم + خارج از پلتفرم) + retention + checksum.
3. **حجم بلوکی جدا** برای دیتا — با حذف instance دیتا نمی‌پرد (`deploy/gozunga/`).
4. **IaC با OpenTofu** — کل سرور با چند دستور بازسازی می‌شود.
5. **تست بازیابی** — حداقل ماهی یک‌بار: سرور آزمایشی، `restore-db.mjs`، چک
   محتوا. بکاپی که هرگز restore نشده، بکاپ نیست.

## ۶) checklist نهایی

- [ ] اگر سایت حیاتی شد: PITR (آرشیو WAL) + Object Lock روی باکت بکاپ اضافه شود
